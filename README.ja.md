# Class Loadout (classloadout)

Minecraft 1.20.1 / Forge 47.x 向けの独立Mod。分隊/パーティー系Modへの依存は一切ない。
プレイヤーは死亡画面から、5つのスロット(メイン武器/サイドアーム/投擲物/ガジェット/近接武器)それぞれに好きなアイテムを自分で割り当てて「マイロードアウト」を作る——ただし割り当てられるのは**OPがそのスロット用にホワイトリスト登録したアイテムのみ**。管理者はさらにGUIエディタで「プリセット」を定義でき、プレイヤーはそれを自分のロードアウトへの出発点として適用し、その後もスロット単位で自由に手を加えられる。リスポーンのたびに、その時点のマイロードアウトがホットバー0〜4番へ自動装備される。

ガジェットスロットには「補給パック」も割り当てられる。2種類あり、**設置型**(右クリックで置く、強め、壊されるか寿命まで残る)と**投擲型**(スノーボールのように投げる、弱め、着弾地点に留まる)。どちらも範囲内のプレイヤーを時間経過で回復/弾薬補充する。弾薬補給はTACZ/SuperbWarfareが導入されていれば連携する(詳細は[設計メモ](#設計メモ)参照)。TACZについては**特定の銃(汎用アイテムではなく)**をロードアウトのスロットに直接選べる。ガジェットスロットにはさらに、[遮蔽物](#遮蔽物)(`classloadout:cover`、HP設定可能・既定1000・誰でも破壊可能なしゃがみ用バリケード)も割り当てられる。死亡画面を経由せずロードアウトを変更したい場合は[ロードアウトステーション](#ロードアウトステーション)ブロックを設置すればいつでも変更できる。

## コマンド

| コマンド | 説明 | 権限 |
|---|---|---|
| `/class assign <slot> <item>` | 自分のロードアウトの1スロット(`main`/`sidearm`/`throwable`/`gadget`/`melee`)をホワイトリスト内のアイテムに設定。`minecraft:air`で解除 | - |
| `/class select <id>` | プリセットの5アイテムを自分のロードアウトへ出発点として反映 | - |
| `/class clear` | 自分のロードアウト全体をクリア | - |
| `/class editor` | プリセットエディタGUIを開く | OP (レベル2+) |
| `/class save <id> <name...>` | プリセットを作成(スロットは空)、または既存プリセットの名前だけ変更(スロットは維持) | OP (レベル2+) |
| `/class save_slot <id> <icon\|main\|sidearm\|throwable\|gadget\|melee> <item>` | 作成済みプリセットの1スロット(またはアイコン)を設定。`minecraft:air`で解除。エディタの[保存]ボタンは`save`1回+`save_slot`6回に分けて送信する(手持ち登録アイテムのIDは長く、6スロット分を1コマンドにまとめるとチャット/コマンドパケットの256文字制限を超えてしまうため) | OP (レベル2+) |
| `/class delete <id>` | プリセットを削除 | OP (レベル2+) |
| `/class whitelist` | スロット別ホワイトリストエディタGUIを開く | OP (レベル2+) |
| `/class whitelist add <slot> <item>` | あるスロットのホワイトリストにアイテムを追加(エディタが送信、手打ち不要) | OP (レベル2+) |
| `/class whitelist remove <slot> <item>` | ホワイトリストからアイテムを削除 | OP (レベル2+) |
| `/class whitelist ammo <slot> <item> <ammoItem> <count>` | ホワイトリスト登録済みのアイテムに弾薬付与を設定。そのアイテムを装備すると(リスポーン時、またはロードアウトステーション/ロッカーでの即時装備時のいずれでも)、`ammoItem`を`count`個プレイヤーの通常インベントリにも付与するようになる。`count`を0にすると解除(ホワイトリストエディタの弾薬付与ポップアップが送信、手打ち不要) | OP (レベル2+) |
| `/class protect` | 死亡時クリア除外アイテムのエディタGUIを開く | OP (レベル2+) |
| `/class protect add <item>` | 除外アイテムリストにアイテムを追加(エディタが送信、手打ち不要) | OP (レベル2+) |
| `/class protect remove <item>` | 除外アイテムリストからアイテムを削除 | OP (レベル2+) |
| `/class spawnkit` | スポーンキットエディタGUIを開く | OP (レベル2+) |
| `/class spawnkit add <item> <count>` | スポーンキットの1エントリを設定(または更新)。以後リスポーンのたびに`item`を`count`個追加で配布するようになる。`count`を0にすると削除(エディタが送信、手打ち不要) | OP (レベル2+) |
| `/class spawnkit remove <item>` | スポーンキットからアイテムを削除 | OP (レベル2+) |
| `/class hammerblocks` | ハンマー範囲破壊の対象ブロックエディタGUIを開く | OP (レベル2+) |
| `/class hammerblocks add <block>` | ハンマー範囲破壊の対象ブロックを追加(エディタが送信、手打ち不要) | OP (レベル2+) |
| `/class hammerblocks remove <block>` | ハンマー範囲破壊の対象ブロックを削除 | OP (レベル2+) |
| `/class guardspawner config <x> <y> <z> <entityType> <delaySeconds>` | 指定座標のガードスポナーブロックを設定(復活させるエンティティ種類・復活までの秒数、エディタが送信、手打ち不要) | OP (レベル2+) |
| `/class guardspawner add_item <x> <y> <z> <item>` | そのガードスポナーの持ち物リストにアイテムを追加(スポーン時にエンティティのアイテムハンドラーに渡される) | OP (レベル2+) |
| `/class guardspawner remove_item <x> <y> <z> <item>` | そのガードスポナーの持ち物リストからアイテムを削除 | OP (レベル2+) |

アイテム引数は登録済みアイテムIDを受け付ける。`minecraft:air` が「未設定」のセンチネル。

**全スロットのホワイトリストは初期状態では空**で、OPがホワイトリストエディタで最低1つアイテムを追加するまで、そのスロットには何も自主割り当てできない。プリセットはホワイトリストの制約を受けない(プリセットエディタに到達できる時点でOPは既にどんなアイテムでも自由に使えるため)。弾薬付与はホワイトリストの各エントリに対する任意設定で、ほとんどのアイテムには設定されない。**除外アイテムリストも初期状態では空**で、OPが除外指定するまで[死亡時の挙動](#死亡時の挙動)のインベントリクリアは全アイテムに及ぶ。

## GUI

- **ロードアウト画面**(バニラ死亡画面右上の「ロードアウト」ボタン): 「マイロードアウト」に自分の5スロットがアイコンとして並び、クリックするとアイテム選択グリッド(検索欄+スクロール一覧、そのスロットのホワイトリストに限定)が開いて直接割り当てられる。下部の「プリセット」には管理者が定義したものが並び、それぞれの[適用]ボタンで5アイテムを自分のロードアウトへコピーできる(適用後もスロットごとに自由に上書き可能)。
- **プリセットエディタ**(`/class editor`、OP限定): 左列に既存プリセット一覧([編集]/[削除])、右列で選択中プリセットの名前・アイコン・5スロットを編集。プリセットエディタのアイテム選択グリッドは**制限なし**(`tacz`/`superbwarfare`/`minecraft`の全アイテム) — ここに到達できる時点でOP権限を持っているため。[保存]を押すまではサーバーに何も送信されず、押した瞬間に1コマンドでプリセット全体が確定する。
- **ホワイトリストエディタ**(`/class whitelist`、OP限定。プリセットエディタからもボタンで直接遷移可): 上部に5つのスロットタブ。スロットを選んでグリッド内のアイテムをクリックするとそのスロットのホワイトリストにON/OFFトグル(登録済みは緑枠で表示)。ここで設定した内容が、プレイヤー向けロードアウト画面のアイテム選択グリッドに直接反映される。**右クリック**すると弾薬付与の設定ポップアップが開く(未登録なら先に自動でホワイトリスト登録)。弾薬アイテムと個数を選んで[保存]で紐付け(設定済みのアイテムはオレンジ色の角マーカーで表示)、[解除]で削除。
- **除外アイテムエディタ**(`/class protect`、OP限定。プリセットエディタからもボタンで直接遷移可): スロットタブは無く単一のグリッド(スロット別ではなく全体で1つのリストのため)。アイテムをクリックすると除外リストにON/OFFトグル(登録済みはオレンジ枠で表示)。用途は[死亡時の挙動](#死亡時の挙動)を参照。
- **スポーンキットエディタ**(`/class spawnkit`、OP限定。プリセットエディタからもボタンで直接遷移可): こちらも単一のグリッド(青枠表示、登録済みセルの角に個数を表示)。クリックで個数1として追加/削除、**右クリック**で個数指定ポップアップを開いて正確な個数を設定できる。用途は[スポーンキット](#スポーンキット)を参照。
- **ハンマー対象ブロックエディタ**(`/class hammerblocks`、OP限定。プリセットエディタからもボタンで直接遷移可): このMod内で唯一「アイテムではなくブロック」を並べる単一グリッド(赤枠表示)。用途は[ハンマー範囲破壊](#ハンマー範囲破壊)を参照。
- **即時装備 + リスポーン時の自動装備**: `assign`/`select`/`clear`はいずれも、コマンドが成功した**その場で**自分のロードアウトの5アイテムを**ホットバー0〜4番**へ(メイン/サイド/投擲/ガジェット/近接の順で)上書き設置する——死ぬ必要はない(死亡画面のロードアウト画面はもちろん、[ロードアウトステーション](#ロードアウトステーション)から生存中に変更した場合も同様)。加えてリスポーン時にも同じ上書きが無条件で走るため、`keepInventory`有効時の重複も起きない。一度もロードアウトに触れていない(assign/select/clearのいずれも未実行の)プレイヤーはそのまま放置される。アイテムが見つからない場合(該当Mod未導入など)はクラッシュせず黙ってそのスロットを空にする。**弾薬付与はリスポーン時のみ**発生する(生存中の即時装備では付与されない)——同じアイテムを生存中に何度も割り当て直すだけで無コストに弾薬を稼げてしまうのを防ぐため、意図的にリスポーンに限定している。装備したアイテムに弾薬付与が設定されていれば、その弾薬も通常インベントリへ追加される(上書きではなく加算、既に持っている分にスタックする)。インベントリに入りきらない分はドロップされる。

## 死亡時の挙動

`death.clearInventoryOnDeath`が有効(既定)の場合、リスポームのたびにプレイヤーの**インベントリ全体**(通常インベントリ・防具・オフハンド)がクリアされる。ただしOPが除外指定した(`/class protect`)アイテムは**基本アイテム種別で一致すれば**(エンチャント・NBT・個数は問わない)クリアの対象外になる。このクリアはロードアウトのホットバー再装備より先に走るため、この設定に関わらずロードアウトの5アイテムは必ず戻ってくる——影響を受けるのはそれ以外の持ち物だけ。同じクリアはロードアウトステーション/ロッカーでの**即時装備**(生存中の割当/選択/クリア)でも走る——生存中に再訪しても、5スロットだけの入れ替えではなくリスポーンと全く同じ挙動になる。

これはバニラの**`keepInventory`ゲームルールを有効にした運用**とセットで使うことを想定している。`keepInventory`が有効なら死亡でアイテムを失わない代わりに、このクリア機能が無いと拾った物が死ぬたびに際限なく積み上がってしまう。逆に`keepInventory`が無効な場合、このMod自身のリスポーン処理が走るより前にバニラが(除外指定の有無に関わらず)アイテムを地面にドロップして失わせてしまうため、除外リストは実質意味を持たない。

即時装備と同じ「ロードアウトに一度も触れていないプレイヤーはそのまま放置」という例外がここにも適用される——`assign`/`select`/`clear`のいずれも未実行のプレイヤーはクリアも含めて一切手を加えられない。

## スポーンキット

**スポーンキット**(`/class spawnkit`)は、**リスポーンのたびに全プレイヤーへ無条件で配布される**アイテム・個数のペアのフラットなリスト——ロードアウトシステムには一切紐づかない。個人ロードアウトの5スロットと違い、ホワイトリスト登録も自己割り当ても、`/class`を一度も触ったことすら不要。誰に対しても常に同じ内容が適用される、固定のスタートキットのようなもの。

- 弾薬付与と同じ加算式の`giveOrDrop`で配布される。既に持っている分にスタックし、入りきらない分はドロップする(何かを上書きすることはない)。
- [死亡時の挙動](#死亡時の挙動)のインベントリクリアとロードアウト装備の**後に**配布されるため、`death.clearInventoryOnDeath`の設定に関わらずスポーンキットのアイテムは必ずそのリスポーンで手元に残る——除外アイテムリストに別途追加する必要は無い。
- 他と同じ`ItemResolver`で解決されるため、単なるアイテム種別だけでなく、既に登録済みの手持ちアイテムバリアントID(ホワイトリストエディタの「手持ちを追加」参照)をエントリに指定することもできる——ただし弾薬付与ポップアップと違い、スポーンキットエディタ自体には新規バリアントを登録するボタンは無い。
- スポーンキットは初期状態では空で、OPが最低1エントリ追加するまで何も配布されない。

## ハンマー範囲破壊

`/class hammerblocks`でホワイトリスト登録したブロックを**SuperbWarfareのハンマー**(どのティアでも可——SuperbWarfare本体への直接依存ではなく、汎用の`#forge:tools/hammer`アイテムタグで判定)で破壊すると、周囲`hammer.hammerAoeRadius`ブロック以内の、同じくホワイトリスト登録されたブロックも爆発のように一緒に破壊される。ただしOPが明示的に許可したブロック種別に限定されるため、地形やビルドを荒らす道具にはならない。

- **実際に破壊したブロック自体もホワイトリストに登録されている必要がある**。登録されていなければ何も起こらず、ハンマーは通常の道具として振る舞う。
- 追加で破壊されるブロックもドロップは通常通り発生する(ハンマー自身のエンチャント、例えば幸運/シルクタッチも反映される)。捨てられたり無効化されたりはしない。
- `hammer.hammerAoeRadius`(既定1)は破壊したブロックを中心とした立方体半径。0にすると範囲効果自体を無効化できる(ホワイトリスト設定はそのまま残せる)。
- ハンマー対象ブロックのホワイトリストは初期状態では空で、OPが最低1ブロック追加するまでハンマーは通常の道具として振る舞う。
- 判定は単なるアイテムタグなので、`#forge:tools/hammer`に対応した他Modのアイテムでも同様に機能する——SuperbWarfare専用にハードコードしているわけではなく、開発の動機になったModというだけ。

## ガードスポナー

`classloadout:guard_spawner`ブロックは、自身の周囲で特定のエンティティを監視し、いなくなった(死亡・despawn等)場合は設定した秒数後にブロックの真上へ再スポーンさせる——SuperbWarfareの車両ガードポストを手動介入なしで維持するのに便利。ブロックを右クリック(OP限定)すると設定GUIが開き、エンティティ種類(登録済みの任意のエンティティID)・復活までの秒数・スポーン時にForgeのアイテムハンドラーケーパビリティ(車両のバッテリー/弾薬スロット等、対応していれば)へ渡すアイテムリストを設定できる。ガードが復活すると全プレイヤーのチャットに通知される。ブロックを破壊すると自身をドロップし、設定も削除される。他のOPエディタと違い設定内容は全クライアントには同期されない——ブロックを右クリックしたプレイヤーだけがそのデータを必要とするため。

## ロードアウトステーション

`classloadout:loadout_station`(ブロック)。**死なずに、いつでもロードアウトを変更できる**設置物。設置して右クリックすると、死亡画面の「ロードアウト」ボタンと全く同じ`LoadoutScreen`が開く——サーバーとの通信が元から無い(ロードアウトデータは既にクライアントへ同期済み)クライアント完結処理のため、ここでも新規パケットは不要。

- 画面内で割当/適用/クリアした内容はその場でホットバーに反映される——[GUI](#gui)節で説明した即時装備と同じ挙動で、死亡画面限定だったものが生存中にも使えるようになるだけ。
- クリエイティブタブ(建築ブロック)から入手可能。現状クラフトレシピは無し(OPが`/give`等で配布する運用を想定)。
- 誰でも右クリックでき、権限チェックは無い(死亡画面のボタンと同じセルフサービス操作のため)。スロットの割り当て自体は通常通りそのスロットのホワイトリストに従う。
- 見た目はプレースホルダーで、作業台の上面テクスチャ(`minecraft:block/crafting_table_top`)を6面に使った単純な立方体。

## 補給パック

`classloadout:health_pack`と`classloadout:ammo_pack`の2種類の設置アイテム。他のアイテムと同じく、OPが`gadget`スロット用にホワイトリスト登録して初めてプレイヤーが割り当て・設置できる。実体はブロックではなくエンティティ(当たり判定で歩行を遮らない、blockstate/model/loot table等のブロック用アセット不要)——アイテム自身の登録モデル(フラットアイコンではなくBlockbench製の3Dボックスモデル)を`ItemRenderer.renderStatic`で地面に据え置き表示する、squadtpのリスポーンビーコンと同じ手法。

- ブロックの面に向かって右クリックすると、その上に設置される。`resupplyIntervalSeconds`秒ごとに、`resupplyRadius`ブロック以内の全プレイヤーを回復(回復パック)または弾薬補給(弾薬パック)する。`packLifetimeSeconds`秒で何もドロップせず自然消滅。
- 1人が同時に設置できるのは`maxActivePacksPerPlayer`個まで(回復・弾薬合算)。超える設置は拒否される。
- 体力1のエンティティとして存在し、**誰の攻撃でも**破壊できる(設置者以外も含む)——classloadoutに分隊/チーム概念は無いため、共有の戦場設置物という扱い。
- **弾薬補給**: TACZは「dummy ammo」方式(`DummyAmmo`NBTタグを持つ銃、`IGun.useDummyAmmo()`)ならその内部弾数を直接補充。それ以外の銃(AK47・M4等TACZ標準銃を含む、いずれもdummy ammoでも`useInventoryAmmo()`でもない"magazine"給弾方式)は、その銃に対応する実弾薬を補充するが、**インベントリ内に対応する弾薬箱(ammo box)が既にあればそちらを優先して補充**(箱自体の上限まで、満タンでもバラ弾へは溢れない)し、該当する弾薬箱が無い場合のみバラ弾アイテムをインベントリへ直接付与する。SuperbWarfareは持っている武器の種類を問わず5種類の弾薬プール(handgun/rifle/shotgun/sniper/heavy)全てを補充する。どちらも非導入なら弾薬パックは何もしない(クラッシュしない)。

## 投擲式補給パック

`classloadout:thrown_health_pack`と`classloadout:thrown_ammo_pack`の2種類の投擲アイテム。上記の設置型より意図的に弱め・気軽な代替として位置づけ(gadgetスロットのホワイトリスト条件は同じ)。

- スノーボール/エンダーパールのように投げる。着弾するとその場に留まり、パーティクルを出して周囲のプレイヤーへ効果を及ぼし始める(設置型より半径は狭く・間隔は長く・寿命は短い、`throwable`セクションのconfig参照)。効果を受けているプレイヤーには毎回action bar通知(「回復中...」/「弾薬補給中...」)が出る。
- **アイテムは消費されない** — `throwCooldownSeconds`(バニラのエンダーパールと同種のアイテムクールダウン)だけが連投を制限するので、クールダウンさえ空けば何度でも投げ直せる。
- 着弾後は設置型と**同じ`maxActivePacksPerPlayer`の枠**を消費する(別枠ではなく合算)。

## 遮蔽物

`classloadout:cover`という設置アイテム。上記2つの補給パックと同じ「エンティティとして設置」方式(壊されるまで残るしゃがみ用の低い壁)だが、効果は一切与えず**高HPのブロッカーとしてそこに立ちはだかるだけ**。ブロックの面に向かって右クリックで設置。

- `coverLifetimeSeconds`(既定600=10分)で自然消滅(補給パックより意図的にずっと長い——消耗品ではなく防御用の構造物のため)。
- 1人が同時に設置できるのは`maxActiveCoversPerPlayer`個まで(補給パックの上限とは別枠)。
- HPは`coverMaxHealth`(既定1000、上限1024——バニラのmax_health属性そのものの上限)。設置した瞬間のconfig値がそのまま適用される。後でconfigを変更しても、既に設置済みの遮蔽物のHPは変わらない(新しく設置したものだけに反映)。
- **誰でも破壊できる**(補給パックと同様)。classloadoutに分隊/チーム概念は無いため、このMod内の設置物はすべて個人の所有物ではなく共有の戦場設置物という扱い。
- 見た目は現状バニラ木材テクスチャを使ったプレースホルダーの低い壁ボックス(`models/item/cover.json`)。他のガジェットと同様、後で専用の3Dモデルに差し替え可能。

## 設定 (`world/serverconfig/classloadout-server.toml`)

- `resupply.resupplyRadius`(既定4) — パック周囲の効果範囲(ブロック)
- `resupply.resupplyIntervalSeconds`(既定2) — 回復/弾薬補給の間隔(秒)
- `resupply.resupplyHealthPerTick`(既定1) — 回復パック1回あたりの回復量(ハーフハート単位)
- `resupply.resupplyAmmoPerTick`(既定10) — 弾薬パック1回あたりの補充量(武器Modごとの単位は[補給パック](#補給パック)参照)
- `resupply.packLifetimeSeconds`(既定20) — 設置から自然消滅までの秒数
- `resupply.maxActivePacksPerPlayer`(既定1) — 1人が同時に持てる上限(回復+弾薬・設置+投擲すべて合算)
- `throwable.throwPackRadius`(既定2) — 意図的に`resupplyRadius`より狭い
- `throwable.throwPackIntervalSeconds`(既定3)
- `throwable.throwPackHealthPerTick`(既定1)
- `throwable.throwPackAmmoPerTick`(既定5) — `resupplyAmmoPerTick`の半分が既定
- `throwable.throwPackLifetimeSeconds`(既定25) — 意図的に`packLifetimeSeconds`より短い
- `throwable.throwCooldownSeconds`(既定15) — プレイヤー・アイテムごとの投擲間隔
- `death.clearInventoryOnDeath`(既定true) — リスポーン時に除外アイテムを除くインベントリ全体をクリアする。詳細は[死亡時の挙動](#死亡時の挙動)参照
- `cover.coverLifetimeSeconds`(既定600) — 遮蔽物が設置から自然消滅までの秒数
- `cover.maxActiveCoversPerPlayer`(既定2) — 1人が同時に持てる遮蔽物の上限
- `cover.coverMaxHealth`(既定1000、上限1024) — 新しく設置する遮蔽物のHP。変更しても既に設置済みの遮蔽物には遡って反映されない
- `hammer.hammerAoeRadius`(既定1) — ハンマーでホワイトリスト登録ブロックを破壊した際、一緒に破壊される立方体半径。0で範囲効果を無効化。詳細は[ハンマー範囲破壊](#ハンマー範囲破壊)参照

## 設計メモ

- **独立した3つの概念、2つのOPツール、1つのプレイヤー画面**: プレイヤー自身のロードアウト(セルフサービス、装備の実体は常にこちら)、OP管理のプリセット(「出発点として読み込む」ための便利ライブラリ、制限なし)、OPが管理するスロット別ホワイトリスト(プレイヤーが自主割り当てできる範囲)。プリセット自体が装備されることはなく、適用は常にプレイヤー自身のロードアウトへのコピーで、ホワイトリストのチェックも受けない(作成できる時点でOP権限を持っているため)。
- **サーバー側での実効的な検証(GUIのフィルタだけではない)**: `/class assign`はサーバー側でそのスロットのホワイトリストと再照合してから受け付けるため、手打ちコマンドでもアイテム選択グリッドの制限を回避できない。
- **サーバー権威・C2Sパケットなし**: プリセット・ホワイトリスト・プレイヤーごとのロードアウトはオーバーワールドに永続化される`SavedData`。`assign`/`select`/`clear`/`save`/`delete`/`whitelist add`/`whitelist remove`の全操作は`/class`コマンド経由でサーバー側検証されるため、なりすませるクライアント→サーバーパケットが存在しない。アイテム一覧もサーバー往復不要: ログイン後クライアントのアイテムレジストリは既に完全なので、`ForgeRegistries.ITEMS`(またはsync済みホワイトリスト)をその場でフィルタするだけ。
- **唯一の例外**: プリセット/ホワイトリスト/除外アイテム/スポーンキット/ハンマー対象ブロックエディタ画面を開く操作。`/class editor`・`/class whitelist`・`/class protect`・`/class spawnkit`・`/class hammerblocks`はサーバー側で実行(そこで権限チェック)され、その1クライアントにだけ小さなトリガーパケットを送り返して画面を開かせる。
- **ロードアウト/ホワイトリスト機構: squadtpと同じ隔離方式のソフト依存**。`compat/TaczCompat`/`compat/SuperbWarfareCompat`は`ModList.isLoaded(...)`の確認のみでTACZ/SW側の型を一切参照しない。実際のAPI呼び出しは`compat/tacz/*`/`compat/superbwarfare/*`だけが持ち、`isLoaded`の分岐内からしかクラスロードされない。この理由で`build.gradle`は両方を`modCompileOnly`としても宣言している(同梱・必須化はしない。純粋な名前空間の文字列判定ではなくなった、という点だけが変化)。
- **TACZの銃は登録アイテムではない——`ItemResolver`が橋渡しする**。TACZは銃1つにつき1アイテムを登録しておらず、全ての銃が同じ汎用アイテム(例: `tacz:modern_kinetic_gun`)で、実際の銃種はNBTの`GunId`タグ経由でTACZのデータ駆動な銃インデックス(`TimelessAPI`)から解決される。つまりTACZの銃としてプリセット/ロードアウト/ホワイトリストに保存される「アイテムID」は実質「銃ID」であり、保存済み`ResourceLocation`を実際の`ItemStack`に変換する箇所(アイコン描画・リスポーン時装備・アイテムピッカーのグリッド自体)は全て`ItemResolver.resolve()`を経由する(TACZの`GunItemBuilder`で銃IDから組み立てを試み、ダメなら通常の登録アイテムとして解決)。`ItemCatalog`もTACZの全銃ID(`TimelessAPI.getAllCommonGunIndex()`)を選択可能なプールに追加している。SuperbWarfareの武器は普通の登録アイテムなので、この橋渡しは不要。
- **弾薬補給**: 同じ`compat/tacz`/`compat/superbwarfare`モジュールが補給パックの弾薬補充(`TaczCompat.resupply`/`SuperbWarfareCompat.resupply`)も担っており、上記と同じガード付きクラスロード方式を共有している。

## ビルド・実行

要件: JDK 21(Gradle実行用。`gradle.properties`の`org.gradle.java.home`で指定)。コンパイルはJava 17 toolchain。

```
gradlew build         # -> build/libs/classloadout-<version>.jar
gradlew runServer      # 開発用サーバー(run-server/)
gradlew runClient      # 開発用クライアント(ユーザー名 "Dev1")
gradlew runClient2     # 2人目の開発用クライアント(ユーザー名 "Dev2"、別ゲームディレクトリ run2/)
```

### 2プレイヤーテスト手順

1. `gradlew runServer`、続けて`gradlew runClient`と`gradlew runClient2`を起動。Dev1をOPにする(`op Dev1`、両エディタに必要)。
2. Dev1側: `/class whitelist` → `main`タブでいくつかアイテムをクリックしてホワイトリスト登録。他のスロットでも1つ以上登録しておく。
3. Dev2側: 死亡→「ロードアウト」→`main`スロットのアイコンをクリックし、Dev1が登録したアイテムだけが表示されること(未登録スロットは「まだ何も許可されていません」の空表示になること)を確認。1つ割り当てると、リスポーンする前でも即座にホットバー0番に入ることを確認。
4. Dev1側: `/class editor` → プリセットを作成(このエディタのアイテム選択グリッドはホワイトリストに関係なく全アイテムが出ることを確認)、保存。
5. Dev2側: 「ロードアウト」→そのプリセットの[適用]→リスポーンして、ホワイトリスト未登録のアイテムが含まれていてもホットバー0〜4番に反映されることを確認(プリセットは仕様上ホワイトリストを迂回する)。
6. Dev1側: 先ほどホワイトリスト登録した中の1つを`/class whitelist`で削除し、Dev2のロードアウト画面のピッカーからそのアイテムが消えること(既存の割り当て自体は遡って解除されず、今後選べなくなるだけ)を確認。
7. `gadget`スロットに`classloadout:health_pack`/`classloadout:ammo_pack`をホワイトリスト登録し、Dev2のロードアウトに割り当ててリスポーン→設置。周囲のプレイヤーが設定間隔で回復/弾薬補給されること、`packLifetimeSeconds`後に消滅すること、`maxActivePacksPerPlayer`を超える設置が拒否されること、Dev1・Dev2どちらが攻撃しても1発で壊れる(友軍制限なし)ことを確認。
8. `classloadout:thrown_health_pack`/`classloadout:thrown_ammo_pack`も`gadget`にホワイトリスト登録→割当→リスポーン→投擲。着弾して効果範囲・間隔が設置型より明らかに控えめであること、action bar通知が出ることを確認。すぐもう一度投げようとして`throwCooldownSeconds`が経過するまでブロックされること、アイテム自体は消費されないことを確認。
9. TACZ導入環境で: `/class whitelist` → `main`タブ → 汎用アイテムだけでなく個々の銃名(例: `tacz:ak47`)がグリッドに並びホワイトリスト登録できることを確認。1つをロードアウトに割り当ててリスポーンし、空の未設定銃ではなく正しい特定の銃がホットバー0番に入ることを確認。
10. `classloadout:cover`を`gadget`にホワイトリスト登録し、Dev2のロードアウトに割り当ててリスポーン→設置。何度攻撃しても(既定HP1000のため)簡単には壊れないこと、`coverLifetimeSeconds`後に消滅すること、`maxActiveCoversPerPlayer`を超える設置が拒否されること、Dev1・Dev2どちらの攻撃でも(友軍制限なく)ダメージが通ることを確認。`coverMaxHealth`を下げて、新しく設置したものだけHPが変わり、既存の設置済みのものは変わらないことを確認。
11. Dev2に`classloadout:loadout_station`を渡し(クリエイティブインベントリまたは`/give`)、生存中に設置→右クリックして、死亡画面の「ロードアウト」ボタンと同じ画面が開くこと、別のアイテムを割り当てると死なずに即座にホットバーへ反映されること、そのアイテムに弾薬付与が設定されていればこの即時反映でも弾薬が付与されること(リスポーン不要。同じアイテムを何度も付け直すたびに毎回付与される仕様)を確認。
12. `/gamerule keepInventory true`を実行。Dev1側: `/class protect`→アイテムをいくつかクリックして除外指定。Dev2側: 除外指定していない適当なアイテムと、除外指定した中の1つを拾ってから死亡→リスポーン。除外していないアイテムは消え、除外したアイテムは残り、ロードアウトの5アイテムはいつも通りホットバーに戻ることを確認。続けて`death.clearInventoryOnDeath`をfalseにして同じ手順を繰り返し、今度は何もクリアされないことを確認。
13. Dev1側: `/class spawnkit`→アイテムを左クリックして個数1で追加、右クリックして別の個数に変更し保存。Dev2側(`/class`を一度も触ったことが無いプレイヤーでも良い): リスポーンして、スポーンキットのアイテムが正しい個数で(既に持っている分にはスタックして)入ることを確認。エントリを削除し、次のリスポーンでは配布されなくなることを確認。
14. SuperbWarfare導入環境で: Dev2にハンマーを渡す(例: `/give Dev2 superbwarfare:hammer`)。Dev1側: `/class hammerblocks`→よくある地形ブロック(例: `minecraft:stone`)をホワイトリスト登録。Dev2がそのブロックをハンマーで破壊し、`hammerAoeRadius`以内のホワイトリスト登録済みブロックも(ドロップ込みで)一緒に破壊されること、未登録の隣接ブロックは無傷であることを確認。続けて未登録のブロックを同じハンマーで破壊しても何も追加で起きない(通常の単体破壊のみ)ことを確認。

`build.gradle`はTACZ/SuperbWarfareを`modRuntimeOnly`(開発クライアント/サーバーに実際にロードさせてテストするため)と`modCompileOnly`(compatクラスが実APIに対してコンパイルできるようにするため)の両方で取り込んでいる。どちらもビルド・配布には不要。
